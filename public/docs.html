Pay another agent

Microdrip sends a USDC payment from one Grok agent to another on Base, using the x402 protocol. In Grok, run the pay-agent skill with /pay-agent.

  • The payee receives the listed price. The buyer pays the 5% fee on top.
  • The minimum payment is $0.10 (100000 atomic USDC).
  • Amounts are atomic USDC strings with 6 decimals: 500000 is $0.50.
  • Only Base USDC is supported (eip155:8453). Microdrip checks EIP-3009 signatures locally and settles through the PayAI facilitator.

Interactive demo

Research bot buys a dataset from Data bot. Press send to run /pay-agent, approve the payment request, and watch the receipt and balances update. Turn on Raw HTTP to see the exact requests, headers, and decoded JSON.

Simulated, no funds move. The demo runs entirely in your browser: no network calls and no keys. Addresses, signatures, and transaction ids are made up, but every request and response has the same shape as the real service, and the fee uses the real rule.

Quickstart

You can do all of this from the home page. The same steps with curl:

Register, create a key, read books
# 1. Register. Prices are atomic USDC: 500000 = $0.50
curl -i -c cookies.txt http://127.0.0.1:4020/v1/register \
  -H "content-type: application/json" \
  -d '{"baseAddress":"0xYourBaseAddress","priceAtomic":"500000","costAtomic":"200000"}'
# 201 {"id":"<recipient id>"} and an mp_session cookie

# 2. Create an API key with that session
curl -b cookies.txt -X POST http://127.0.0.1:4020/v1/keys
# 201 {"apiKey":"mp_<64 hex>"}

# 3. Read your books
curl http://127.0.0.1:4020/v1/books -H "Authorization: Bearer mp_..."

Share your recipient id with bots that should pay you. Keep the API key secret: it identifies your registration on every call.

How a payment works

  1. Ask. The buyer calls POST /v1/payments with its key, the recipient id, and the listed price.
  2. Challenge. Microdrip answers 402 with a Base USDC challenge in the PAYMENT-REQUIRED header. Its amount is the buyer total: the listed price plus the 5% fee.
  3. Sign. The buyer signs two EIP-3009 authorizations: the listed price to the recipient Base address (payTo), and the fee to the platform (extra.feePayTo). It retries with both in PAYMENT-SIGNATURE and leaves the challenge amount unchanged.
  4. Settle. Microdrip verifies both signatures and settles both transfers. The payment finishes only when both settle.
  5. Receipt. The answer is 200 with a PAYMENT-RESPONSE receipt. The payee's /v1/books credit goes up by the listed price.

When platformBaseAddress in config.json is empty, the service returns 503 platform_unconfigured and no challenge, so the payment stays unavailable.

Pay another agent with /pay-agent

The pay-agent skill (.grok/skills/pay-agent/SKILL.md) sends a payment from one Grok agent to another on this service. Tell the skill who pays, who is paid, and the listed price:

  • Who pays: the sender's API key, sent as Authorization: Bearer.
  • Who is paid: the recipient id from registration (not a Base address).
  • Listed price: the atomic amount the payee receives, at least 100000. It is not the buyer total.

The skill handles the challenge, signs both authorizations, retries, and reports the receipt. That is exactly what the demo walks through.

API reference

All bodies are JSON. Amounts are strings of atomic USDC. Authenticated routes take Authorization: Bearer <apiKey>.

POST

/v1/register

Registers the address that gets paid. Sets an HttpOnly mp_session cookie used by /v1/keys.

Request → 201
POST /v1/register
content-type: application/json

{"baseAddress":"0xYourBaseAddress","priceAtomic":"500000","costAtomic":"200000"}

HTTP/1.1 201 Created
set-cookie: mp_session=...; HttpOnly; Path=/; SameSite=Lax

{"id":"<recipient id>"}
POST

/v1/keys

Creates an API key for the registration in the session cookie. The key is returned once.

Request → 201
POST /v1/keys
cookie: mp_session=...

HTTP/1.1 201 Created

{"apiKey":"mp_<64 hex>"}
GET

/v1/books

Reads the books for the key's registration. creditedAtomic is the listed price times settled payments. feeAtomic is the fees buyers paid to the platform on those payments.

Request → 200
GET /v1/books
Authorization: Bearer mp_...

HTTP/1.1 200 OK

{"creditedAtomic":"500000","feeAtomic":"25000","settledCount":1,"priceAtomic":"500000","costAtomic":"200000"}
POST

/v1/payments

Pays another registered agent. The first call returns the challenge. The retry with PAYMENT-SIGNATURE settles it.

1. Ask → 402
POST /v1/payments
Authorization: Bearer <sender key>
content-type: application/json

{"recipient":"<recipient id>","amount":"500000"}

HTTP/1.1 402 Payment Required
PAYMENT-REQUIRED: eyJ4NDAyVmVyc2lvbiI6Mi... (base64 JSON, see Payment headers)

{"error":"PAYMENT-SIGNATURE header is required"}
2. Retry with signatures → 200
POST /v1/payments
Authorization: Bearer <sender key>
content-type: application/json
PAYMENT-SIGNATURE: eyJ4NDAyVmVyc2lvbiI6Mi... (base64 JSON)

{"recipient":"<recipient id>","amount":"500000"}

HTTP/1.1 200 OK
PAYMENT-RESPONSE: eyJzdWNjZXNzIjp0cnVl... (base64 JSON)

{"settled":true,"amount":"500000","network":"eip155:8453","recipient":"<recipient id>"}
GETPOST

{{resourcePath}}

The metered resource for a merchant. Send the merchant's key. It costs that merchant's registered price, with the same 402, sign, and retry flow. It answers 503 if the price is not above the cost or is under the minimum.

Paid response → 200
HTTP/1.1 200 OK
PAYMENT-RESPONSE: eyJzdWNjZXNzIjp0cnVl...

{"delivered":true,"service":"microdrip","unit":"request"}

Payment headers

Each header is base64 of UTF-8 JSON.

PAYMENT-REQUIRED (the challenge)

accepts has one Base entry. amount is the buyer total. extra.feeAmount is the 5% fee and extra.feePayTo is the platform address. extra.name and extra.version name the EIP-712 domain, and asset is the verifying contract.

PAYMENT-REQUIRED, decoded
{
  "x402Version": 2,
  "error": "PAYMENT-SIGNATURE header is required",
  "resource": {
    "url": "http://127.0.0.1:4020/v1/payments",
    "description": "Metered HTTP response",
    "mimeType": "application/json",
    "serviceName": "microdrip"
  },
  "accepts": [
    {
      "scheme": "exact",
      "network": "eip155:8453",
      "amount": "525000",
      "asset": "0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913",
      "payTo": "<recipient Base address>",
      "maxTimeoutSeconds": 300,
      "extra": {
        "name": "USD Coin",
        "version": "2",
        "feeAmount": "25000",
        "feePayTo": "<platform Base address>"
      }
    }
  ]
}

PAYMENT-SIGNATURE (the retry)

Copy accepts[0] into accepted unchanged. Sign each authorization as EIP-712 TransferWithAuthorization with chainId 8453. validAfter must be before now and validBefore after now. The two nonces must differ.

PAYMENT-SIGNATURE, decoded
{
  "x402Version": 2,
  "accepted": { "...": "accepts[0] from the challenge, amount still 525000" },
  "payload": {
    "authorization": {
      "from": "<buyer address>",
      "to": "<payTo>",
      "value": "500000",
      "validAfter": "0",
      "validBefore": "<now + 300>",
      "nonce": "0x<32 random bytes>"
    },
    "signature": "0x<65-byte EIP-712 signature>",
    "feeAuthorization": {
      "from": "<buyer address>",
      "to": "<extra.feePayTo>",
      "value": "25000",
      "validAfter": "0",
      "validBefore": "<now + 300>",
      "nonce": "0x<different 32 random bytes>"
    },
    "feeSignature": "0x<65-byte EIP-712 signature>"
  }
}

PAYMENT-RESPONSE (the receipt)

transaction is the payee transfer, feeTransaction is the platform fee, and amount equals the quote.

PAYMENT-RESPONSE, decoded
{
  "success": true,
  "transaction": "0x<payee transaction>",
  "feeTransaction": "0x<fee transaction>",
  "network": "eip155:8453",
  "payer": "<buyer address>",
  "amount": "525000"
}

Errors

Errors are JSON: {"error":"<code>"}. A 402 always carries a fresh PAYMENT-REQUIRED challenge whose error field repeats the reason.

Request errors

StatusCodeMeaning
400invalid_jsonThe body is not valid JSON.
413body_too_largeThe body is over 64 KB.
400base_address_invalidRegistration needs a 0x address with 40 hex characters.
400price_invalid / cost_invalidPrice and cost must be whole atomic USDC strings.
401session_required/v1/keys needs the session cookie from registration.
401api_key_requiredNo Authorization: Bearer key was sent.
401unknown_api_keyThe key does not belong to any registration.
400recipient_requiredrecipient is missing.
404recipient_unknownNo registration has that recipient id.
400recipient_is_senderAn agent cannot pay itself.
400amount_invalidamount must be a positive whole atomic USDC string.
400 / 503amount_below_minimumThe amount, or the merchant's price, is under $0.10.
503price_not_above_costThe merchant's price is not strictly above its cost, so nothing is sold.
503platform_unconfiguredThe operator has not set platformBaseAddress.
404not_foundUnknown route.
405method_not_allowedThe resource only takes GET or POST.
500server_error / settlement_failedSomething failed on the server.

Payment errors (402)

CodeMeaning
PAYMENT-SIGNATURE header is requiredThe first, unpaid call. Sign the challenge and retry.
malformed_paymentThe header is not base64 JSON, or fields are missing or badly formed.
wrong_versionx402Version must be 2.
unsupported_schemeOnly the exact scheme with EIP-3009 authorizations is accepted.
network_mismatchOnly eip155:8453 (Base) is accepted.
wrong_assetThe asset or EIP-712 domain is not Base USDC.
wrong_recipientThe payee authorization is not to payTo.
amount_mismatchaccepted.amount was changed, or the payee value is above the price.
value_below_priceThe payee authorization is below the listed price.
expired / not_yet_validNow is not strictly between validAfter and validBefore.
bad_signatureA signature does not recover to from.
fee_requiredThe fee authorization or signature is missing.
fee_payer_mismatchThe fee must come from the same buyer.
wrong_fee_recipientThe fee is not to extra.feePayTo.
fee_mismatchThe fee value is not extra.feeAmount.
fee_reusedThe fee nonce repeats the payee nonce.
nonce_replayedThe nonce was already used. A replay of a settled payment gets its original receipt instead.
settle_failedSettlement did not go through. The facilitator's own reason, such as invalid_exact_evm_insufficient_balance, may appear instead.
missing_transaction / missing_fee_transactionSettlement returned no transaction id, so nothing is credited.

Run locally

Terminal
npm install
# Set platformBaseAddress in config.json to the operator's Base address first
npm start
# open http://127.0.0.1:4020

# Tests (browser tests need Chrome)
CHROME_PATH=/usr/bin/google-chrome npm test

Payments are real USDC on Base mainnet. Start the local service with npm start, then open http://127.0.0.1:4020. https://microdrip.xyz does not serve payments.
